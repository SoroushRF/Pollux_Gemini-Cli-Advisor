## 1. Scope and Boundary

In scope (from guideline):

- canonical settings schema definition and type inference,
- settings validation (Zod) and normalization,
- user / workspace / system / system-defaults / schema-defaults merge logic,
- CLI-side settings-to-core `Config` mapping via `loadCliConfig`,
- configuration storage and path resolution.

Out of scope:

- detailed policy rule behavior (compartment 09),
- model routing internals (compartment 07),
- UI rendering of settings dialog.

The compartment adds two observable boundaries that the guideline assumes but
does not name explicitly:

- **CLI is the sole owner of settings.** Core never reads settings files, only
  consumes a `ConfigParameters` struct. This is significant because
  `POLLUX_SPEC.md` claims settings live in `config.ts` (ambiguous between CLI
  and core); the correct owner is CLI.
- **Schema-to-JSON export is a generator, not a runtime dependency.**
  `schemas/settings.schema.json` is regenerated by
  `scripts/generate-settings-schema.ts` from the same `SETTINGS_SCHEMA` constant
  and is only used for editor autocompletion.

## 2. Runtime Flow Summary

1. **Entry**: CLI calls `loadSettings(workspaceDir)` in
   `packages/cli/src/config/settings.ts:643-650`. Results are memoised in a
   10-second cache keyed by absolute workspace path (`settings.ts:622-625`).
2. **Resolve file paths**:
   - User: `Storage.getGlobalSettingsPath()` → `~/.gemini/settings.json`
     (`settings.ts:79`, `storage.ts:69-71`).
   - System: `getSystemSettingsPath()` — platform-specific defaults, overridable
     via `GEMINI_CLI_SYSTEM_SETTINGS_PATH` (`settings.ts:98-109`).
   - SystemDefaults: sibling of system settings, filename
     `system-defaults.json`; overridable via `GEMINI_CLI_SYSTEM_DEFAULTS_PATH`
     (`settings.ts:111-119`).
   - Workspace: `new Storage(workspaceDir).getWorkspaceSettingsPath()` →
     `<cwd>/.gemini/settings.json` (`storage.ts:281-283`). **Skipped when
     `cwd == home`** to avoid treating the home directory as a project
     (`settings.ts:723-725`, `storage.ts:158-163`).
3. **Load each file** through the inner `load(filePath)` helper
   (`settings.ts:667-713`):
   - `fs.existsSync` → `fs.readFileSync` → `stripJsonComments` → `JSON.parse`.
   - Non-object JSON produces a fatal settings error.
   - Valid objects are Zod-validated via `validateSettings`
     (`settings-validation.ts:280-287`). Validation failures are recorded as
     **warnings**, not fatal errors.
   - JSON parse errors are recorded as severity `error` and will trigger
     `FatalConfigError` after all files are loaded (`settings.ts:778-786`).
4. **Environment variable substitution**: each scope is passed through
   `resolveEnvVarsInObject` (`settings.ts:735-738`). An `originalSettings` clone
   is kept for save-round-tripping without variable interpolation.
5. **Trust check**: a preliminary merge of defaults + system-defaults + user +
   system settings is built with `customDeepMerge` and fed to
   `isWorkspaceTrusted(initialTrustCheckSettings, workspaceDir)`
   (`settings.ts:753-762`). Only trusted workspaces get to contribute settings.
6. **Env file load**: `loadEnvironment` walks upward from `workspaceDir` looking
   for `.gemini/.env` then `.env`, falling back to `$HOME/.gemini/.env` and
   `$HOME/.env` (`settings.ts:497-524`, `552-619`). Excluded variables and
   sandbox whitelisting are honoured.
7. **Final merge**:
   `mergeSettings(system, systemDefaults, user, workspace, isTrusted)` produces
   a `MergedSettings` via `customDeepMerge` in the precedence order
   **schemaDefaults < systemDefaults < user < safeWorkspace < system**
   (`settings.ts:247-273`, `deepMerge.ts:83-96`). Untrusted workspaces are
   replaced with `{}`.
8. **Legacy theme rewrite**: `VS`/`VS2015` theme names are rewritten to current
   defaults (`settings.ts:741-750`).
9. **Admin overlay**: `LoadedSettings.computeMergedSettings()` applies remote
   admin overrides on top of the file-merged result every time
   `setRemoteAdminSettings` runs (`settings.ts:365-390`). File-based admin
   settings are discarded.
10. **Migration**: `migrateDeprecatedSettings` rewrites legacy boolean
    inversions (e.g. `disableAutoUpdate → enableAutoUpdate`) and
    `migrateExperimentalSettings` moves experimental blocks to their canonical
    parents (`settings.ts:834-1060`, `1106-1233`).
11. **CLI parameter assembly**:
    `loadCliConfig(settings, sessionId, argv, options)` combines merged settings
    with parsed CLI flags, env vars, sandbox config, memory discovery, extension
    manager, and trust check. Returns a fully-populated `new Config(params)`
    (`packages/cli/src/config/config.ts:520-1026`).
12. **Core ingestion**: `Config.constructor`
    (`packages/core/src/config/config.ts:960-1393`) stores parameters into
    private fields, assembles sandbox defaults (including
    `Storage.getGlobalTempDir()`), wires `SandboxPolicyManager`,
    `ModelConfigService`, `WorkspaceContext`, and registers event listeners.
    `Config.initialize()` (`config.ts:1393-1466`) then resolves
    `Storage.initialize()` (which migrates hash-based project dirs to
    slug-based) and populates registries.

## 6. Risks and Regression Hotspots

- **Risk**: Adding a new top-level settings block without regenerating
  `schemas/settings.schema.json` leaves the IDE autocompletion out of sync,
  which is not caught by runtime tests.
  - Severity: medium.
  - Why fragile: editor UX drift is silent until a user opens a broken
    autocomplete; the generator is a separate manual command.
  - Mitigating test: `scripts/tests/generate-settings-schema.test.ts:22-43`
    supports `--check` which can be wired into CI.
  - Suggested guard: run `npm run schema:settings -- --check` in CI for every PR
    touching `settingsSchema.ts`.

- **Risk**: Changing `mergeStrategy` on an existing array key (e.g.
  `UNION → CONCAT`) silently changes the merged result without any compile-time
  error.
  - Severity: high.
  - Why fragile: `getMergeStrategyForPath` reads the schema at runtime; any
    strategy change produces different merged values without a type break.
  - Mitigating test: `packages/cli/src/config/settings.test.ts:979-1092` covers
    a handful of array merges but does not enumerate all UNION/CONCAT paths.
  - Suggested guard: a schema-invariant test that walks `SETTINGS_SCHEMA` and
    asserts every array-type setting has an explicit `mergeStrategy`.

- **Risk**: `loadSettings` cache hides mid-session writes that happen from other
  processes (e.g. another CLI invocation editing `~/.gemini/settings.json`).
  - Severity: medium.
  - Why fragile: 10-second TTL + clear-on-save is process-local; cross-process
    edits are invisible for up to 10s.
  - Mitigating test: none observed.
  - Suggested guard: document the TTL in `settings.ts`; optionally drop the
    cache when the file's mtime changes.

- **Risk**: `migrateExperimentalSettings` mutates settings on read-only
  (`system`) scopes and emits a warning, but the merged result already reflects
  the migration in RAM. A downstream consumer may receive a migrated value that
  is not present on disk.
  - Severity: medium.
  - Why fragile: divergence between "what the admin intends" and "what runtime
    sees" is user-hostile when debugging.
  - Mitigating test: none observed in sampled tests.
  - Suggested guard: skip in-RAM migration for read-only scopes (only emit the
    warning); require the admin to migrate explicitly.

- **Risk**: `ConfigParameters` is an open-ended struct with ~150 fields and no
  schema. Adding a field in core and forgetting to wire it in `loadCliConfig` is
  silent.
  - Severity: high.
  - Why fragile: TypeScript tolerates `undefined` on optional fields; runtime
    will default to `undefined` and downstream feature flags silently fall back
    to legacy behaviour.
  - Mitigating test: `packages/core/src/config/config.test.ts` exercises the
    constructor, but does not assert that every field has a settings-to-params
    binding.
  - Suggested guard: build a test that walks `ConfigParameters` keys and asserts
    each one is either (a) set by CLI args/env, (b) set from settings, or (c)
    explicitly documented as "intentionally defaulted".

- **Risk**: `BrowserAgentCustomConfig` (core) and `agents.browser` (CLI schema)
  drift without a programmatic check.
  - Severity: medium.
  - Why fragile: two manual sources of truth; the doc comment is the only guard.
  - Mitigating test: none.
  - Suggested guard: generate the core type from the CLI schema via the existing
    generator script.

## Appendix B: New-Setting Implementation Recipe (Step 7)

To safely add a new settings block (example: hypothetical `pollux`):

1. **Declare in CLI schema** — add a top-level object to `SETTINGS_SCHEMA` in
   `packages/cli/src/config/settingsSchema.ts`. Use `type: 'object'`, provide
   `label`, `category`, `requiresRestart`, a concrete `default`, `description`,
   and nest per-field definitions under `properties`. For array fields, set
   `mergeStrategy` to `UNION` or `CONCAT` as appropriate; for records keyed by
   user-supplied strings, use `additionalProperties` +
   `mergeStrategy: SHALLOW_MERGE` (mirror `mcpServers` for precedent).
2. **Keep the `$ref` library in sync** — if a sub-type is reused, add it to
   `SETTINGS_SCHEMA_DEFINITIONS` so both the generated JSON schema and
   `settings-validation.ts` see it.
3. **Regenerate** — run `npm run schema:settings` to refresh
   `schemas/settings.schema.json`. Run `npm run docs:settings` to refresh
   `docs/get-started/configuration.md`. Commit both artefacts.
4. **Validation** — no action needed. `settings-validation.ts` rebuilds the Zod
   schema from `SETTINGS_SCHEMA` at module load; a new block is picked up
   automatically. Add explicit `settings-validation.test.ts` cases for the
   block's happy and unhappy paths.
5. **Merge tests** — add cases to `packages/cli/src/config/settings.test.ts`
   that exercise default/user/workspace/system precedence for the new keys,
   especially for arrays or records where the wrong `mergeStrategy` is a silent
   bug.
6. **Wire into `ConfigParameters`** — extend
   `packages/core/src/config/config.ts` `ConfigParameters` with the new fields.
   Add matching private fields and accessors on `Config`. Do not read settings
   files from core.
7. **Map in `loadCliConfig`** — extend
   `packages/cli/src/config/config.ts:897-1026` to forward the new settings into
   `new Config({...})`. Respect the **argv > env > settings > default**
   precedence rule.
8. **Feature flag first** — new invasive features should gate themselves under
   `experimental.*` first, then migrate to a top-level block once stable. Use
   `migrateExperimentalSettings` (`settings.ts:1106-1233`) as the template.
9. **Trust + admin** — decide whether the block is allowed in workspace scope
   (it will be zeroed out in untrusted folders automatically) and whether it
   should be gated by `admin.*` (e.g. `admin.skills.enabled` for skills).
10. **Consumer wiring** — add the new value to every site that reads it. Prefer
    accessor methods (`Config.getX()`) over reading the raw parameter; accessors
    give a single migration point if the shape changes.
11. **Docs** — update `docs/get-started/configuration.md` via the generator, add
    a dedicated feature doc if the surface is user-facing.
12. **No-op default verification** — add a regression test that loading an empty
    `~/.gemini/settings.json` produces the same merged value as the schema
    default for the new block.

## Appendix C: Anti-Patterns (Step 8)

- **Adding a core-only settings field.** Core must not read settings files. Any
  field that bypasses the CLI schema is invisible to the IDE, the docs,
  validation, migration, and the admin overlay. Evidence: the `ConfigParameters`
  struct is dotted with optional fields that look runtime-only but every
  production value flows through `loadCliConfig`.
- **Reading raw CLI args inside core.** `CliArgs` is a CLI-only contract
  (`packages/cli/src/config/config.ts:77-129`). Core should depend only on
  `ConfigParameters`. A leak here couples CLI parsing to core semantics.
- **Hand-writing paths to `~/.gemini/...`.** All path derivation must go through
  `Storage` / `paths.ts`. Tests rely on `GEMINI_CLI_HOME` and
  `GEMINI_CLI_SYSTEM_SETTINGS_PATH` overrides; bypassing `Storage` breaks test
  isolation.
- **Mutating `loadedSettings.merged` directly.** Only `LoadedSettings.setValue`
  should write, because it reseeds the merged view, saves the file, and fires
  `coreEvents.emitSettingsChanged()`.
- **Relying on env-var resolution surviving a round-trip.** Resolved values live
  in `.settings`; original file shape lives in `.originalSettings`. Write only
  to the original; never persist the resolved clone.
- **Changing a `mergeStrategy` without migration.** Switching from `REPLACE` to
  `UNION` for an existing key silently rewrites user data. Always ship a
  compatibility shim or a migration.
- **Adding settings without running the schema generator.** Users lose IDE
  autocompletion and docs; CI does not currently enforce this (see Risk § for
  suggested guard).
- **Treating `admin.*` as user-writable.** It is remote-only
  (`settings.ts:374-389`).
- **Assuming `~/.gemini/settings.json` is the only layer.** There are four
  loadable scopes plus a Session scope for extensions; migrations and
  validations must consider all four.
- **Writing to settings from inside a hot path.** `saveSettings` clears the
  cache (`settings.ts:1064`); rapid writes trigger rapid re-reads and the cache
  provides no throttle.
