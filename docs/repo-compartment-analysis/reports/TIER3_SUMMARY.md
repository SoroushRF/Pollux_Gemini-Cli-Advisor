## 2. Compartment summaries

### 2.1 Compartment 05 — Extensibility (Skills, Hooks, Commands)

**Key claim**: there are **11 hook events**, **three command loaders active
interactively**, **two active non-interactively** (skills dropped), and
extensions are trust-gated at install, load, and runtime.

**Hook event taxonomy** (VT-05.1, `hooks/types.ts:43-55`): 11 values —
`BeforeTool`, `AfterTool`, `BeforeAgent`, `Notification`, `AfterAgent`,
`SessionStart`, `SessionEnd`, `PreCompress`, `BeforeModel`, `AfterModel`,
`BeforeToolSelection`.

**Trust double-gate on project hooks** (VT-05.2):

1. Registration skipped when workspace is untrusted
   (`hooks/hookRegistry.ts:172-187`).
2. Runtime execution returns failure under the same condition
   (`hooks/hookRunner.ts:64-79`).

**Interactive slash chain** (VT-05.3, `slashCommandProcessor.ts:326-332`):
`BuiltinCommandLoader → SkillCommandLoader → McpPromptLoader → FileCommandLoader`.

**Non-interactive slash chain** (VT-05.3 cont.,
`nonInteractiveCliCommands.ts:43-48`): Builtin + McpPrompt + File.
**SkillCommandLoader is omitted.**

**SlashCommandResolver rules** (VT-05.4, `SlashCommandResolver.ts:46-204`):

- Built-in command names are **always preserved verbatim**.
- Extension-file and skill-with-extension names are **always prefixed**.
- Collisions force renaming via `getPrefix`.

**Extension installation gating** (VT-05.5,
`extension-manager.ts:217-232, 183-210`): requires workspace trust; remote
sources gated by `allowedExtensions` regex and `blockGitExtensions` rule.

**Extension hooks off by default** (VT-05.6, `extension-manager.ts:883-889`):
`settings.hooksConfig.enabled = false` by default. When enabled, payloads pass
through `recursivelyHydrateStrings`.

**Observability**: all 11 `HookEventName` values plus extension-manager
install/error logs.

**Contradictions**:

- **C-05.1** (`deferred → 01`): non-interactive drops `SkillCommandLoader`;
  intent unverified.
- **C-05.2** (`unresolved`): `POLLUX_SPEC.md` §10 Phase 7 names `/pollux`; no
  `pollux` identifier exists in `packages/cli/src`.

**Top risks**:

- **R-05.1 (medium)**: `/pollux` in `BuiltinCommandLoader` alone invisible to
  ACP (separate registry, see 12).
- **R-05.2 (medium)**: `/pollux` shipped as a skill invisible non-interactively
  (skills dropped).
- **R-05.3 (low)**: Pollux-as-hook off by default until
  `hooksConfig.enabled = true`.
- **R-05.4 (low)**: `extensions-reload.test.ts` skipped — reload semantics
  unverified.

**Coverage gaps**:

- Non-interactive `/pollux` reachability (R-05.1, R-05.2).
- Extension reload semantics (R-05.4).
- No parity assertion between CLI and ACP slash registration.

### 2.2 Compartment 09 — Policy, Trust, and Safety Engine

**Key claim**: `PolicyDecision` is a closed `{allow, deny, ask_user}` enum
evaluated first-match-wins after priority sort; default is **DENY
non-interactive / ASK_USER interactive**; YOLO short-circuits to ALLOW.
Synthetic tools have no special-case exemption.

**Engine shape** (VT-09.1, `policy/types.ts:10-14`, `policy-engine.ts:745-748`):
`CheckResult` carries exactly one `PolicyDecision` per call.

**Matching** (VT-09.2, `policy-engine.ts:565-661`):

1. Collect rules applying to the current `FunctionCall.name` (aliases + MCP FQN
   resolved — VT-09.6, `policy-engine.ts:47-194, 492-563`).
2. Sort by priority.
3. First-match-wins.
4. Default: DENY non-interactive, ASK_USER interactive.
5. YOLO mode short-circuits to ALLOW (before step 1).

**Workspace policy integrity** (VT-09.3, `cli/config/policy.ts:108-160`): load
is **gated on folder trust AND integrity hash**. Modified workspace TOML →
re-prompt via `policy/integrity.ts:40-114`.

**Extension policy restriction** (VT-09.4, `policy/config.ts:225-282`):
extensions **cannot** grant `ALLOW` or YOLO rules. Loader strips them on import.
Pollux cannot ship its own allow-rule via an extension.

**Two enforcement sites** (VT-09.5):

1. `scheduler._processToolCall` via `scheduler/policy.ts:checkPolicy`
   (`scheduler/scheduler.ts:617-678`).
2. `MessageBus.publish` for `TOOL_CONFIRMATION_REQUEST`
   (`confirmation-bus/message-bus.ts:90-137`).

A tool reaching both paths can **prompt twice**.

**Guideline corrections** (both `resolved`):

- C-09.1 — actual consumer is `scheduler/scheduler.ts`, not
  `core/coreToolScheduler.ts`.
- C-09.2 — `FolderTrustDiscoveryService` is consumed by UI/extension flows, not
  the engine directly; the engine couples to trust only via `trustedFolders.ts`.

**Top risks (all Pollux-relevant)**:

- **R-09.1 (high)**: `advisor_consultation` synthetic tool → default DENY
  non-interactive unless packaged-default TOML ALLOW rule ships. **Synthesis
  SR-5.**
- **R-09.3 (medium)**: double-prompt from dual enforcement sites. Suggested:
  route advisor through scheduler path only.
- **R-09.2 (medium)**: dynamic policy updater appends ALLOW rules at runtime;
  per-turn Pollux updates could grow unbounded. Suggested: prohibit Pollux from
  emitting `UPDATE_POLICY` messages.
- **R-09.4 (low)**: extension-stripped ALLOW means Pollux allow-rule must ship
  built-in or admin — document the channel explicitly.

**Coverage gaps**:

- No test for advisor-style synthetic tool double-prompt avoidance (R-09.3).
- No Pollux feature-flag-scoped policy bundle (R-09.1).
- No published guidance on which channel ships the Pollux allow-rule (R-09.4).

### 2.3 Compartment 12 — Output Protocol and ACP Adapters

**Key claim**: `OutputFormat` is a closed enum with 3 values, the JSONL event
taxonomy is a closed enum with 6 values, neither includes an advisor /
escalation type; the ACP command surface is a **separate**, narrower registry.

**`OutputFormat`** (VT-12.1, `output/types.ts:9-13`): `text`, `json`,
`stream-json`.

**JSONL stream event types** (VT-12.1 cont., `output/types.ts:28-116`): `init`,
`message`, `tool_use`, `tool_result`, `error`, `result`. **No advisor or
escalation event exists today.**

**`JsonFormatter.format`** (VT-12.2, `json-formatter.ts:12-52`): builds
`JsonOutput` with optional `session_id`, ANSI-stripped response, stats, error →
`JSON.stringify(..., null, 2)`. `formatError` reuses the same path.

**`StreamJsonFormatter`** (VT-12.3, `stream-json-formatter.ts:24-34`): one
minified JSON object + newline per event. **Ordering is enforced by callers, not
by the formatter itself.**

**Parallel non-interactive drivers** (VT-12.4, `nonInteractiveCli.ts:317-370`

- `nonInteractiveCliAgentSession.ts:418-591`): legacy and agent-session drivers
  emit the same JSONL contract from **two different upstream event unions**
  (`GeminiEventType` vs `AgentEvent`). A new JSONL event must be added to both
  translators or it silently drops from one.

**ACP command surface** (VT-12.5, `acp/acpClient.ts:692-735` +
`acp/commands/commandRegistry.ts:23-38`): accepts `/` and `$` prefixes, routes
through ACP-only `CommandHandler` registry (Memory, Extensions, Init, Restore,
About, Help). **Does not** share any loader with the interactive
`CommandService` chain.

**Unknown event drops** (VT-12.6, `nonInteractiveCliAgentSession.ts:593-602`):
`session_update`, `custom`, and other non-output `AgentEvent` types are
explicitly ignored — future Pollux events on `custom` are invisible to this
driver.

**Contradictions**:

- **C-12.1** (`deferred → 03`): two parallel non-interactive drivers translate
  distinct event unions to the same JSONL contract.
- **C-12.2** (`unresolved → 13`): ACP and non-interactive command surfaces are
  disjoint.

**Top risks**:

- **R-12.1 (medium)**: adding a Pollux advisor/escalation event requires
  coordinated change to `JsonStreamEventType` **and** both non-interactive
  drivers; absent that, escalations drop silently.
- **R-12.2 (medium)**: ACP uses `connection.requestPermission` (not the policy
  engine); a synthetic advisor tool surfaces an **unexpected permission
  prompt**. Cross-links to 09 R-09.1 in synthesis SR-5.
- **R-12.3 (medium)**: agent-session non-interactive driver silently ignores
  unrecognized `AgentEvent` types — `custom`-kind Pollux events vanish.
- **R-12.4 (medium)**: `StreamJsonFormatter` performs no sequencing; Pollux
  interceptor must be **strictly upstream** of formatter calls.

**Coverage gaps**:

- No `JsonStreamEventType` for advisor/escalation (R-12.1, R-12.3).
- No regression that both non-interactive drivers emit identical JSONL for
  equivalent input (C-12.1).
- ACP advisor permission flow not exercised (R-12.2).

## 3. Cross-cutting themes (Tier-3)

### 3.1 Command + output + policy surfaces fragment **into** Pollux

Each T3 compartment surfaces a different fragmentation axis that Pollux must
handle:

| Surface            | Axes that fragment                                          | Synthesis risk   |
| ------------------ | ----------------------------------------------------------- | ---------------- |
| Slash commands     | interactive / non-interactive / ACP / A2A (four registries) | SR-4             |
| JSONL events       | legacy driver / agent-session driver (two translators)      | SR-1 side-effect |
| Permission prompts | policy engine (scheduler + bus) / ACP `requestPermission`   | SR-5             |
| Doc + status       | spec ledger / code / priority table / CODEOWNERS            | SR-7             |

The unifying observation is that **Pollux cannot ship as "one place that does
the thing"**; each surface requires its own registration or explicit
out-of-scope statement.

### 3.2 Every T3 compartment owns a closed enum Pollux wants to extend

- 05: `HookEventName` — 11 values. Adding advisor events as a new hook kind
  touches every `HookEventName` switch.
- 09: `PolicyDecision` — 3 values (`allow`/`deny`/`ask_user`). Pollux cannot add
  `bypass` without changing the enum contract; the suggested guard in R-09.3 is
  _classification_ (non-prompting), not a new decision.
- 12: `OutputFormat` + `JsonStreamEventType` — 3 and 6 values. Advisor +
  escalation either reuse `tool_use`/`tool_result` or add new enum members
  (R-12.1).
- 16: forensic F-IDs — 10 entries. F-05/F-06 are unmapped governance orphans.

Recommendation (synthesis cluster C, F): **reuse existing enum values where
semantically compatible** (e.g., `tool_use` for advisor call,
`LlmRole.UTILITY_ADVISOR` for telemetry, non-prompting classification for
policy) and _extend_ only when necessary.

### 3.3 Non-interactive mode is the stricter surface for Pollux

Across 05 + 09 + 12 three asymmetries bite Pollux:

| Surface                        | Interactive                  | Non-interactive                                               |
| ------------------------------ | ---------------------------- | ------------------------------------------------------------- |
| Slash loaders                  | Builtin+Skill+McpPrompt+File | Builtin+McpPrompt+File (skill dropped)                        |
| Policy default (no rule match) | `ask_user`                   | **`deny`**                                                    |
| ACP permission prompt          | allowed (human present)      | silent failure                                                |
| Unknown `AgentEvent`           | rendered somehow             | silently dropped (`nonInteractiveCliAgentSession.ts:593-602`) |

Pollux rollout must choose non-interactive as the primary validation surface;
interactive leniency hides failures.

### 3.4 Extensions are a restricted channel, not a Pollux shipping channel

09 VT-09.4 and R-09.4 together: extensions **cannot** grant ALLOW or YOLO.
Therefore Pollux allow-rule for `advisor_consultation` must ship as either
**built-in policy** (packaged default TOML) or **admin policy**
(`adminPolicyPaths`). Spec §10 Phase 7 silently assumes extensibility covers
this; it does not.

### 3.5 Docs-vs-code drift is the silent cross-cutting risk

16 R-16.1 + 07 C-07.3 + 11 C-11.1 + 14 C-14.1 + 15 C-15.1 all land in the same
place: the authoritative docs encode claims that are known-false at the code
level. Synthesis SR-7 aggregates these. The mitigating control — per-F-ID doc-PR
list (NA-7) — must exist before or alongside the first Pollux PR that would make
any of those claims true.

### 3.6 Trust and integrity are already baked in — Pollux inherits them

Workspace trust (09 VT-09.3) is **doubly gated**: folder trust + integrity hash.
A modified workspace TOML triggers a re-prompt. Pollux does not need to
re-implement any of this; it only needs to ensure its packaged default rule
lives outside the workspace-scoped policy (so integrity-hash re-prompts do not
silently disable the advisor).

### 3.7 Tier-3 observability signals

| Layer              | Signals                                                                                                           |
| ------------------ | ----------------------------------------------------------------------------------------------------------------- |
| Extensibility (05) | All 11 `HookEventName` values, extension-manager install/error logs                                               |
| Policy (09)        | `MessageBusType.TOOL_CONFIRMATION_REQUEST`, `MessageBusType.UPDATE_POLICY`, `scheduler.checkPolicy` decision logs |
| Output/ACP (12)    | All 6 `JsonStreamEventType` values, `ACP connection.sessionUpdate`                                                |
| Docs/gov (16)      | `docs-audit` workflow PRs, `docs-rebuild` runs, `INDEX.md` row state changes                                      |

Pollux additions should be observable through **existing** channels:
`BeforeModel`/`AfterModel` hooks for advisor, `tool_use`/`tool_result` JSONL for
advisor call, `scheduler.checkPolicy` decision logs for the allow-rule match.

## 5. Pollux-relevant design implications

Taken verbatim from T3 contradictions + escalated open questions.

1. **Ship the advisor ALLOW rule as built-in policy** (09 R-09.1 → NA-3): a
   packaged-default TOML rule gated on the Pollux feature flag. Do not ship via
   an extension (extensions are stripped of ALLOW/YOLO — VT-09.4).
2. **Classify advisor as non-prompting in the policy engine** (09 R-09.3 →
   NA-3): avoids the dual-prompt from scheduler + confirmation bus.
3. **Route advisor through the scheduler path only** (09 R-09.3 → NA-3):
   explicit `isSynthetic` tag to short-circuit ACP
   `connection.requestPermission` (12 R-12.2).
4. **Register `/pollux` in all four command surfaces** (05 R-05.1/R-05.2 →
   NA-6): Builtin + ACP + A2A. Do **not** ship as a skill (non-interactive drops
   it).
5. **Reuse `tool_use`/`tool_result` JSONL events for advisor** (12 OQ-12.1 →
   NA-3): tag with `LlmRole.UTILITY_ADVISOR` in telemetry rather than extending
   `JsonStreamEventType`. Minimizes surface area of coordinated changes.
6. **Produce per-F-ID doc-PR list in `POLLUX_DOC_CORRECTIONS.md`** (16 R-16.1 →
   NA-7): each doc PR keyed to the Pollux PR that makes the claim true.
7. **Add CODEOWNERS for `POLLUX_*.md` and `docs/repo-compartment-analysis/`**
   (16 R-16.3 → NA-7): ensure spec drift gets a reviewer.
8. **Version header on `POLLUX_SPEC.md` + `IMPLEMENTATION_PLAN.md`** (16
   OQ-16.1, escalated from 15 OQ-15.1 → NA-7): automate at release time.
9. **Prefix spec sections with `implemented? yes/no/partial`** (16 R-16.4):
   one-time cleanup as part of NA-7 lands.
